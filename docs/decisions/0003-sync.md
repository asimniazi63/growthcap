# 0003: T3 sync slice (schema, paged sync, orders/create)

*2026-10-31. First slice of T3. Metrics, the six tools, the cron refresh, the `/connect` counts and `reconcile:truth` are not built yet.*

## Rulings
- **Paged GraphQL, not a bulk operation**, as the build plan says. Pages are small (5 products, 10 orders) to stay under Shopify's 1000-point query cost; an order or product whose nested connection overflows its page throws instead of being stored partly.
- **Customers come from orders only.** `customers` holds a pseudonym (`CUST_` + 16 hex of sha256(tenant:shopify id)) and `first_seen_at`. No name, email, phone or address column exists anywhere, and no GraphQL document asks for one (two tests).
- **Orders are dated by `processedAt`** (falling back to `createdAt`) in the shop's time zone, stored as `local_date`. Seeded orders carry the import time as `createdAt`.
- **Upsert only, never delete.** A resync after the 60-day window keeps rows Shopify stops returning. The same `upsertOrder` serves the sync and the webhook, so a duplicate or simultaneous `orders/create` repeats the same write.
- **`orders/create` re-fetches the order by id** from the payload's `admin_graphql_api_id` and ignores every other payload value. The tenant is the verified shop's. A fetch that finds nothing throws, so the route answers 500 and Shopify retries.
- `WebhookCtx` now carries `db`.

## Known gaps
- An order edited in Shopify to remove a line keeps the old line row (upsert only).
- A list of more than 20 lines on one order throws; no follow-up paging yet.
- Nothing calls `syncStore` yet: the `/connect` Resync button and the nightly cron are next.
- `orders/create` is in `shopify.app.toml` but live only after `shopify app deploy` (Asim runs it). The migration `drizzle/0001_*.sql` runs by hand with `npm run db:migrate`.

## Slice 2: the metric engine (`lib/metrics`, `lib/tools/result.ts`)

*Built and tested against `truth.json` for both stores. The other five tools, the cron refresh, the Resync button, `/connect` counts and `reconcile:truth` are still to do.*

### Rulings
- **One registry** (`registry.ts`) defines the 11 core metrics; `queryMetric` reads it, and `scripts/seed/truth.ts` computes the same definitions independently from the dataset. `repeat_rate` and `zero_sales_days` are T12 and are skipped by the storyline checks.
- **Fixtures go through the real code path.** `scripts/fixtures/load-db.ts` serves a dataset as Admin GraphQL nodes from a fake Shopify and runs `syncStore`, so the metric tests cover the sync and the mappers too. Both stores sit in one test database as two tenants, which makes the isolation tests meaningful.
- **Folded in memory, not in SQL.** `queryMetric` reads the tenant's order lines for the range plus every refund, and folds them in TypeScript. That is fine at demo scale (1,024 orders) and keeps each definition readable. The production plan moves it into SQL.
- **Cancelled orders are left out** of every metric. The seeded stores have none.
- **A refund counts on its own day** for `refunds` and `net_sales` (including inside day, week and month groups), and in the order's period for `refund_rate`.
- **Zero-fill** only for a single day, week or month grouping, between the first and last order dates. A range wholly outside that window is `NO_DATA`; a quiet stretch inside it is zeros.
- **`compareTo`** uses the previous calendar month for a whole month, otherwise the same number of days before; `previous_year` keeps a whole month whole. It can't be combined with a time grouping (`INVALID_INPUT`).
- **`share`** is returned for metrics that add up, when grouped by a non-time dimension. For `tag` and `product` an order can sit in several groups, so shares are of the groups' sum.
- **Input** is a strict Zod schema: unknown keys (a tenant, a shop) are rejected. `limit` accepts up to 500 and returns at most 200 rows, with `truncated` set.
- Added to the plan's filters: `tags` and `variantIds`, because the storyline checks need them.

### Known gaps
- Refund line values in the fixtures use the same rounding as `truth.ts`. The live stores' refund values are compared in `reconcile:truth`, which is not built yet.
- No `collection` dimension or filter yet.
- Metric definitions have not been compared with Shopify Analytics (spike (c)), so `docs/metrics.md` doesn't list differences yet.

## Slice 3: the other five tools (`lib/tools`)

*`getOrders`, `searchProducts`, `getInventory`, `getCustomers` and `describeMetrics`, each with an exported strict Zod schema. With `queryMetric` that is the six tools of T3. Not built: the cron refresh, the Resync button and `/connect` counts, `reconcile:truth`, a live sync.*

### Rulings
- **Shared plumbing** is in `lib/tools/common.ts` (strict input parsing, the data window, named periods, `NO_DATA`, query ids, the 200-row cap). `queryMetric` was moved onto it; its tests still pass.
- **Every tool checks the connection first** (`STORE_DISCONNECTED`), then validates input. The tenant is always `ctx.tenantId`; every query filters on it, and a test removes each filter in turn to prove the isolation tests fail without it.
- **Store text is returned under `untrusted`** (tags, notes, product and variant titles, descriptions, location names) and kept out of the top-level fields. An order's note comes back only for a single order id with `includeNote: true`.
- **`getOrders`** asks for orders by date, discount code, channel, tag, product, variant, customer pseudonym, customer type or refund, and sorts newest, oldest or largest. Looking up order ids with no dates ignores the date range. One order id returns its lines and refunds. Default 50 rows, at most 200, with `truncated.total`.
- **`searchProducts`** matches the title (case-insensitive; `%` and `_` are plain characters) and returns price, unit cost, and the margin worked out.
- **`getInventory`**: days of cover = available ÷ (units sold in the window ÷ window days). Window is 7, 14, 30 (default), 60 or 90 days ending on the store's "today". Units are before refunds. A variant with no sales has `daysOfCover: null` and sorts last; `maxDaysOfCover` leaves those out.
- **`getCustomers`**: `summary` gives active, new (first-ever order in the range) and returning (first order before it) customers; `list` ranks by spend or orders (default 10 rows). Customers appear only as `CUST_` pseudonyms. Its returning count differs from the `returning_customer_rate` metric, and the definition says so.
- **Catalogue and stock tools** report the day they were last synced as their `range`, because they have no date range.
- **`describeMetrics`** returns the registry, the groupings and periods the tools accept, and the unit conventions (money in cents, rates as fractions).

### Known gaps
- `getOrders` for a single order does not refresh from Shopify (the product plan says it should). It reads the synced copy.
- `searchProducts` has no collection filter, and there is no `collection` dimension yet.
- No cohort view in `getCustomers` (that is `repeat_rate`, T12).
- `queryMetric` group values for `tag` and `discount_code` are store-made text and come back in `group`, not under `untrusted`. Short codes and tag names, but T4's prompt and number checker must still treat them as data.
- `npm run eval` does not exist yet (T4), so it was not run for this change to `lib/tools`.

## Slice 4: syncing from the app, the nightly job and `reconcile:truth`

*Built and tested without any live call. Not yet run against the real stores: that needs a deploy, then a Resync on each store.*

### Rulings
- **A sync is a recorded run.** `beginSync` writes a `running` row (or says `already_running` / `not_connected`), `executeSync` does the work and never throws (the outcome is on the row), and `startSync` hands the slow part to Next's `after()` so the request returns at once. A run with no result after 15 minutes is marked abandoned and no longer blocks a new one. Two simultaneous callers could both start (no database lock); the second run only repeats the same upserts.
- **Who can resync:** `gc_admin` and `gc_partner`. A `client_viewer` cannot. Connecting a store stays admin-only.
- **A sync starts when a store is connected** (the OAuth callback) and from the Resync button on `/connect`. The page shows counts (orders, customers, products, variants, refunds), the order date span, "data as of" in the store's time zone, and the last run's outcome, and refreshes itself every 10 seconds while a run is going.
- **Nightly job:** `GET /api/cron/refresh`, scheduled in `vercel.json` for 07:00 UTC, checks `CRON_SECRET` (timing-safe; no secret configured means no access) and re-runs the paged sync for every connected store in turn. One store failing does not stop the others. Vercel runs crons on production deployments only. The daily inventory snapshot from the implementation plan is **not** built (no `inventory_snapshots` table): nothing uses history yet.
- **`reconcile:truth`** (`scripts/reconcile/`) compares every month x 11 metrics, the storyline checks the core metrics can answer, and five row counts (orders, refunds, products, variants, customers) with `truth.json` and the dataset, through the same `queryMetric` the agent uses. It writes one section per store to `docs/evals/reconciliation.md`, lists each difference with its explanation from `scripts/reconcile/explanations.ts` or the word UNEXPLAINED, and exits 1 if any are unexplained. A month with no synced orders is one difference. Storyline checks on products and variants need the loader's journal (`.seed-journal/<store>.json`) to map generator ids to Shopify ids; without it they are listed as not checked. Read-only.

### Known gaps
- Functions run for at most 300 seconds (`maxDuration`). A full Solenne sync (about 1,024 orders in pages of 10) has not been timed against the real API. If a function is killed mid-run, the run shows `running` for up to 15 minutes and a Resync is refused until then; the rows already written stay.
- Query sizes (10 orders with up to 20 lines, 5 products with up to 25 variants) have not met Shopify's cost limit yet. A rejected query fails the run with Shopify's message.
- Order edits that remove a line, and refunds Shopify later deletes, are not removed from the synced copy (upsert only).
