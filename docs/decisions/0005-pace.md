# 0005: Pace (T6)

Decisions made while building T6, newest last. T6 follows `docs/build-plan.md` T6 and implementation plan T5-A.

## Slice 1: ad spend, plans and the two ad metrics (2026-10-31)

- **Where the data comes from.** `plan.csv` and `ad-spend.csv` are loaded into Postgres by `npm run fixtures:load` (`--check` only validates the files). Both files are validated in full before any write, a bad row stores nothing, and loading the same file again leaves the same rows. Calendar and call notes are not loaded here: they belong to T7 (Why).
- **Tables.** `ad_spend` (tenant, date, channel, spend in cents), `plans` (one active plan per brand, `source` fixture or upload) and `plan_targets` (month, metric, value; money in cents, the rate as a fraction). A reload manages only the fixture plan, so a later uploaded plan is never overwritten. The plan's name column is called `label`, because the personal-data schema test rejects any column called `name`.
- **MER and new-customer CAC** are in the metric registry (so `query_metric` and `describe_metrics` have them). MER = net sales ÷ ad spend; CAC = ad spend ÷ new-customer orders. Both are 0 when the divisor is 0, as AOV is, and their definitions say so.
- **Ad spend is split by time only.** The ad platforms' spend can't be assigned to a product, code or customer, so MER and CAC can be grouped by day, week or month (one at a time) and anything else is `INVALID_INPUT`. Order filters narrow the net sales but never the ad spend, and the definition says that.
- **Tested against `truth.json`.** `truth.json` has no ad figures, so the test takes net sales and new-customer orders from it and the ad spend from `ad-spend.csv` read line by line, and checks MER and CAC for every month of both stores. Mutation checks: reading spend across tenants, reading spend outside the range and removing the grouping rule each fail a test.
- **Not done yet in T6:** `gapToPlan`, `/pace`, `render_view`, pinned views, saved threads, memories. `plan.csv` also holds months after the data ends (to the end of 2026), which the month-end estimate will need.

## Slice 2: gapToPlan and /pace (2026-10-31)

- **`gapToPlan` on metric rows.** `query_metric` adds it when the result is the whole store (no grouping, no filters) over part or all of one calendar month and the brand's active plan has a target for that month. Per metric it carries the month's `target`, `planned` for the days in the range, `actual`, `gap`, `pctGap`, `throughDate`, and for a month to date (range starts on the 1st, ends before the last day) `projected`. A range that spans two months, a grouped or filtered result, or a month the plan doesn't cover gets no `gapToPlan`: a filtered actual can't be held against a whole-store target.
- **Two kinds of target.** Totals and counts (net sales, orders, new-customer orders) build up over the month, so the target is spread over its days. Average order value and the returning-customer rate are the same size all month, so the month's target is held against the figure for any part of it, with no spreading and no estimate.
- **The spread** follows the same month last year, day by day, using that metric's own daily values (a day with a net refund counts as zero). If the data doesn't cover that whole month (Tidepool has no October 2025, and the dataset starts 2025-11-01), the target is spread evenly and `spread` says `even`. A month with a different length gets the average day for any day last year's month didn't have.
- **The month-end estimate** is the plan's formula: actual so far + the rest of the plan × (actual ÷ plan so far). It is null before any of the plan has come due, and it has no range or backtest (cut in the ticket).
- **Rounding.** Money to whole cents, counts to one decimal, rates to four, and the gap is computed from the rounded figures so that actual, planned and gap add up when quoted. The number checker reads `gapToPlan` by the metric it belongs to (cents to dollars, `pctGap` as a percentage).
- **`/pace` counts complete days only:** this month through yesterday, so a day in progress doesn't read as a shortfall. On the first day of a month (also the morning after a demo store's data ends) nothing is complete, so the page says the month hasn't started and shows last month. It uses the same query as the agent (`getPaceView` calls `queryMetric`), so the page and the chat can't disagree. Note the agent's "this month" runs through today, so its month-to-date plan includes today's share.
- **Roles.** Every role sees /pace for their own brand, as with the chat.
- **Not yet:** the gauge and other approved components for chat answers (`render_view`), pinned views, saved threads and memories are the next slices.

## Slices 3 to 6: views, pinned views, saved threads, notes (2026-10-31)

Built together, with the review and the live checks left to the end of the ticket.

- **`render_view` draws what a tool returned; the model types no numbers.** Its input is a component (kpi, line, bar, table, gauge or waterfall; anything else is refused), a title of at most 80 characters and one to three `queryRefs`. A ref must be the query id of a `query_metric` result from the same turn, so a view can't be drawn from data the model invented or from another turn. `buildView` copies the figures out of those results (`lib/views/build.ts`) and each component says what it needs when a result doesn't fit (a line needs one day, week or month grouping; a gauge needs `gapToPlan`; a waterfall needs `compareTo`, one grouping, a metric whose groups add up, and every group). The numbers go to the browser in a `data-view` part and the model only gets `{ rendered: true }` back, so a chart doesn't cost the data twice in tokens. A number in the title must be in the results (the number checker runs on it).
- **No chart library.** The components are plain markup and SVG, each with an `aria-label` that gives the figures and a "Show the numbers" table. Money is formatted from cents, a change is said in words ("down 28.3%"), and store text (a product title) is only ever rendered as text.
- **Pinned views keep the query, not the data.** `saved_views` holds the component and the tool plus input behind it. Pinning runs the queries once for the signed-in brand (so a view that can't be drawn is refused), and every load of `/pace` runs them again, so a pinned "this month" is always this month. The input goes through `query_metric`'s strict schema again, so a tenant or any invented field is refused. A person pins their own views (up to 12); nobody else can list or remove them.
- **Threads store the provider's messages, not the screen.** `thread_messages` holds each message exactly as the provider returned it (tool calls, tool results, reasoning blocks and their signatures), grouped by turn, and the model sees the last 10 turns, cut between turns only. The earlier messages the browser sends are ignored: for a saved thread only the newest question is taken from the request, which also stops a forged assistant message from entering the history. The per-turn context (today's date, notes) is stored with the question it was sent with, so replays are byte-identical and the cache prefix doesn't change. The repair exchange (first draft, the checker's instruction, the corrected answer) is saved in order. The display copy is built from the server's own stream (`onEnd` of the UI stream), not sent by the browser. A new thread is written only after its first answer succeeds; a failed turn saves nothing.
- **Notes need a person.** `remember` (offered to the two Growth Capital roles only) saves a proposal; the chat shows it with Confirm and Dismiss. Only confirmed notes reach the model, as a labelled line in the turn context. A note can't hold a link or a Shopify id, at most 280 characters, 10 waiting and 20 confirmed per brand. Confirming, dismissing and removing need a Growth Capital admin or partner; a client viewer can read the confirmed notes on the chat page. The confirmation is the defence against a note the model was talked into by store text.
